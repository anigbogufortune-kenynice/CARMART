# Auth and Security

> Generated by /write-specs from `issues/prd-carmart.md` (Q2, Q9, Q11, Q19).

## Authentication method

- **Provider:** Supabase Auth, using `@supabase/ssr` cookie sessions in Next.js (App Router).
- **Sign-up and sign-in:**
  - Email and password. Passwords must be 10+ characters, and Supabase's leaked-password protection is enabled.
  - **Email verification is required.** Unverified users can browse, but can't message, save, report or create a shop (AC-02).
  - **Google OAuth.** Accounts created this way are treated as email-verified (AC-03).
- **Phone verification (sellers only):** an Australian mobile (`+614XXXXXXXX`) is verified by SMS OTP through Supabase phone auth (`updateUser({ phone })` → `verifyOtp({ type: 'phone_change' })`), with Twilio as the SMS provider. It's required before a shop can be submitted for approval (AC-06). The phone is **not** a sign-in method.
- **Password reset:** Supabase `resetPasswordForEmail` → `/auth/reset` page.
- **Sessions:** refreshed in `src/middleware.ts` using the `@supabase/ssr` middleware helper. Access tokens last 1 hour; refresh tokens rotate.

## Flows

**Sign up (email)**
1. The user submits email, password and display name → `supabase.auth.signUp` (email redirect to `/auth/callback?next=/`).
2. The `handle_new_user()` trigger creates `profiles` (`role = user`, `status = active`).
3. The user clicks the email link → `/auth/callback` exchanges the code → session set → redirect.

**Sign in:** `signInWithPassword` or `signInWithOAuth({ provider: 'google', redirectTo: /auth/callback })`.

**Sign out:** `supabase.auth.signOut()` → redirect to `/`.

**Become a seller:**
1. Create a shop (`draft`), then draft listings.
2. Verify the phone.
3. Submit the shop, wait for admin approval, then submit listings. See `docs/systems/shop-onboarding.md`.

## Roles

| Role | How assigned | Capabilities |
|---|---|---|
| anonymous | — | Browse live listings, approved shops, and legal pages |
| `user` | Default on sign-up | Plus: message shops, save cars, report, create one shop |
| shop owner | A `user` with a row in `shops` | Plus: manage own shop, listings and photos, and reply to buyers |
| `admin` | **Only** by migration or seed SQL (`update profiles set role = 'admin' …`); no API or UI can set it (AC-05) | Plus: every `/admin` queue and action, settings, audit log |

A **suspended** profile (`status = 'suspended'`) gets 403 `ACCOUNT_SUSPENDED` on every `user`-level route, and middleware redirects it to `/suspended` for protected pages (AC-52).

## Authorisation layers (defence in depth)

1. **Middleware** (`src/middleware.ts`): refreshes the session and redirects unauthenticated users away from protected page routes to `/sign-in?next=…`.
2. **Route handler**: Zod parse → `getUser()` (**never** trust `getSession()` alone on the server) → verified email + active status → role/ownership check → service call.
3. **Service layer**: enforces business rules and state transitions (for example, only an owner can submit their listing, and only from allowed states).
4. **Postgres RLS**: the last line of defence on every table (see `docs/schema.md`). Status transitions happen only through `security definer` RPCs that re-check `auth.uid()`.

## Secrets and keys

- `SUPABASE_SERVICE_ROLE_KEY` is read **only** by `src/server/jobs/**` (the background job runner behind `/api/internal/*`) and by seed/admin scripts in `scripts/`. An ESLint `no-restricted-imports` rule forbids importing `src/server/jobs/**` or the service-role client from anywhere else, and a test asserts it (ADR-006).
- The vendor API keys (Anthropic, Sightengine, Resend) are server-only env vars read only by `src/server/jobs/**`. The browser never sees them, and user-facing route handlers never call the vendors.
- All secrets come from the environment (`docs/env.md`), validated at startup by `src/lib/env.ts`.

## Rate limits

| Action | Limit | Where |
|---|---|---|
| Sign-in / sign-up / OTP | Supabase Auth built-in limits (configured in the dashboard) + 5 SMS codes per user per hour | Supabase / `profile.service` |
| Photo uploads | 60 per shop per rolling 24 h | `upload_events` |
| New conversations | 20 per buyer per rolling 24 h | `start_conversation` RPC |
| Messages | 60 per user per hour | `messaging.service` |
| Reports | 10 per user per rolling 24 h | `create_report` RPC |

## Privacy (Australian Privacy Act)

- All photo metadata (EXIF, GPS, XMP) is stripped before any image becomes public (AC-25).
- The seller's phone is shown only when they opt in, and only to signed-in users (AC-48).
- Data is hosted in the Sydney region (`ap-southeast-2`).
- Account deletion is out of scope for v1 self-service. It's handled by request via the Contact page, and an admin runs the documented deletion procedure. Support address: `support@carmart.example` (**placeholder**, replace before launch; see the launch checklist in `docs/architecture.md`).
